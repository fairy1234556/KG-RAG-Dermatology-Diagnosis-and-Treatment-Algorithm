# V1.0 分阶段开发计划

## 1. 总体策略

V1.0 在当前研究仓库内增量建设，不创建独立新仓库。开发顺序调整为：

1. 研究代码适配与核心后端。
2. 数据库和病例基础。
3. 候选排序、KG-RAG、模板降级和一致性校验。
4. 医生端核心页面。
5. 医生审核与报告。
6. 患者端。
7. 后台、实验、测试、软著和论文材料。

必须长期保留：

- `kg/`
- `rag/`
- `work/`
- `outputs/`
- `experiments/`

当前阶段不修改原始 CSV、不覆盖实验输出、不伪造图像分类能力。

## 2. 阶段一：研究代码适配与核心后端

目标：把现有 Demo 能力封装为后端服务层，保持研究代码可复用，并为完整分析编排接口预留主入口。

主要任务：

1. 创建 `backend/` 基础结构。
2. 建立配置模块，统一读取 KG CSV 路径。
3. 封装 `KnowledgeGraphQuery` 为图谱查询服务。
4. 封装 `EvidenceContextBuilder` 为证据上下文服务。
5. 封装 `KGRAGPromptBuilder` 和 V2 Prompt 为 Prompt 服务。
6. 增加结构化 JSON 输出，不只返回 Markdown 文本。
7. 提供模板生成适配器，保证模型不可用时仍可演示。
8. 规划完整分析编排接口 `POST /api/cases/{case_id}/analysis-runs`。
9. 编写图谱查询和 Prompt 构造的基础测试。

交付物：

- 后端服务骨架。
- 图谱查询接口。
- 证据上下文接口。
- Prompt 构造接口。
- 模板降级生成接口。
- 完整分析编排接口设计。

验收点：

- 七类 HAM10000 疾病均可查询基础证据。
- 输入典型特征可反查相关候选疾病。
- 证据上下文包含路径、证据文本和来源。
- 不改变现有 Demo 和 CSV。

优先级：P0。

## 3. 阶段二：数据库和病例基础

目标：建立 SQLite + SQLAlchemy 业务存储，支撑用户、角色、匿名患者、病例、观察、图片、语义锚点和基础版本记录。

主要任务：

1. 建立 SQLAlchemy 基础配置。
2. 实现用户、角色、匿名患者、病例、观察表。
3. 增加研究人员角色 `researcher`，仅访问实验和研究相关模块，不访问未经授权的患者病例。
4. 实现图片元数据表和文件存储目录。
5. 实现语义锚点表。
6. 实现图谱、Prompt、模型、算法版本表。
7. 实现操作日志表。
8. 实现病例状态流转：草稿、分析中、待审核、已审核、已归档。

交付物：

- SQLite 数据库结构。
- 病例 CRUD 接口。
- 观察保存接口。
- 图片上传和预览接口。
- 语义锚点保存能力。
- 基础版本记录。
- 操作日志基础能力。

验收点：

- 医生可创建虚拟病例并保存临床观察。
- 病例编号唯一。
- 图片可上传、预览、删除并关联病例。
- 病例和后续分析记录可关联图谱、Prompt、模型、算法版本。
- 归档不删除历史审计数据。

优先级：P0。

## 4. 阶段三：候选排序、KG-RAG、模板降级和一致性校验

目标：形成完整后端分析链路：语义锚点识别 -> 候选排序 -> 证据召回 -> KG-RAG 或模板生成 -> 声明校验 -> 报告草稿。

主要任务：

1. 实现候选疾病规则化排序。
2. 使用公式 `Score(d) = αMf + βMl + γMs + ηCe - λCf`。
3. 输出 `feature_score`、`site_score`、`symptom_score`、`evidence_coverage_score`、`conflict_penalty`。
4. 明确风险提示不参与候选疾病排序，只在候选疾病形成后单独生成。
5. 明确未填写、未知、未观察不能作为冲突惩罚。
6. 只有用户明确描述且与图谱证据矛盾时，才计入 `conflict_penalty`。
7. 实现单跳和多步证据路径召回。
8. 将 Prompt 模板迁移到 `prompts/` 目录管理。
9. 实现医生端 KG-RAG 生成接口和模板降级生成逻辑。
10. 实现医学声明拆分、路径映射和图谱匹配。
11. 实现 `supported`、`partially_supported`、`unsupported`、`not_verifiable` 标记。
12. 实现 OEHR、UCR、PCS、ECR 和明细计数字段。
13. 实现完整分析编排接口 `POST /api/cases/{case_id}/analysis-runs`。
14. 保留细分接口，供调试、实验和后台研究使用。

交付物：

- 候选排序服务。
- 证据路径召回服务。
- KG-RAG 解释服务。
- 模板降级服务。
- 证据一致性校验服务。
- 报告草稿生成服务。
- 完整分析编排接口。

验收点：

- 候选疾病分数明确标注不是患病概率。
- 风险提示不参与候选疾病排序。
- 不支持声明可被标记。
- `not_verifiable` 单独记录，不自动算作 `supported`。
- 模型关闭时仍能通过模板生成结构化辅助解释。

优先级：P0。

## 5. 阶段四：医生端核心页面

目标：完成医生端最小可用页面闭环。

主要任务：

1. 创建 `frontend/` 基础结构。
2. 实现登录和角色路由。
3. 实现医生工作台。
4. 实现病例列表。
5. 实现新建/编辑病例表单。
6. 实现图片上传、预览和删除组件。
7. 实现语义锚点确认和人工修正组件。
8. 实现候选疾病 Top-3 页面。
9. 实现分析结果页。
10. 实现证据路径详情组件。

交付物：

- 医生端 P0 页面。
- 病例录入到分析结果查看的前端流程。
- 分项评分展示组件。
- 证据路径详情组件。

验收点：

- 医生能在单一病例流程中完成录入、分析和结果查看。
- 候选疾病分数明确标注不是患病概率。
- 医生端可以查看风险依据，但必须标明风险提示不是疾病概率。
- 医生审核前，系统结果只作为候选疾病和辅助解释。

优先级：P0。

## 6. 阶段五：医生审核与报告

目标：完成医生审核、报告版本和导出闭环。

主要任务：

1. 实现医生审核页。
2. 实现报告详情页。
3. 实现医生审核草稿和最终提交。
4. 增加 `status=draft/submitted` 和 `decision=approved/revised/rejected/needs_followup`。
5. 确保 `submitted_at` 仅最终提交时填写。
6. 实现报告版本关系：`report_group_no`、`parent_report_id`、`is_current`。
7. 落实唯一约束 `UNIQUE(case_id, report_group_no, version_no)`。
8. 系统原始版本和医生修订版本分开保存，不得覆盖系统原始报告。
9. 实现报告导出和打印视图。

交付物：

- 医生审核页面。
- 报告详情页面。
- 报告版本服务。
- 报告导出能力。

验收点：

- 医生提交审核后保留系统原始输出和医生修订版本。
- 草稿审核不写入 `submitted_at`。
- 当前报告版本可通过 `is_current` 标识。
- 报告包含图谱、Prompt、模型和算法版本。

优先级：P0。

## 7. 阶段六：患者端

目标：提供补充性的患者健康信息查询流程。

主要任务：

1. 实现患者端免责声明确认。
2. 实现自查信息录入页。
3. 实现患者端图片上传和预览。
4. 实现患者端语义锚点和范围判断。
5. 实现通俗解释生成。
6. 实现关注与就医提示。
7. 实现本人历史记录页，可后置。

交付物：

- 患者端说明页。
- 自查录入页。
- 通俗结果页。
- 关注与就医提示组件。

验收点：

- 患者端不显示最终诊断。
- 患者端不输出处方、剂量或确定性治疗建议。
- 患者端不展示医生端完整候选评分和专业指标。
- 患者端就医建议固定使用“需常规关注”“建议预约皮肤科评估”“建议尽快就医评估”。
- 超范围、证据不足或需要尽快评估的信息优先提示线下就医。
- 规则得分、相似度或候选排序不表述为确诊概率。

优先级：P1。

## 9. 风险与控制

| 风险 | 控制措施 |
|---|---|
| Demo 代码导入路径不稳定 | 服务层使用适配器统一导入，逐步迁移稳定逻辑 |
| CSV 字段不规范 | 加载时做字段清洗和空表头容错，原文件不改 |
| 规则评分被误解为概率 | 页面、接口和报告均强制展示非概率说明 |
| 风险提示被误用为排序特征 | 风险提示在候选疾病形成后单独生成，不参与候选排序 |
| 未观察信息被误判为冲突 | 未填写、未知、未观察不能计入冲突惩罚 |
| 模型输出无证据声明 | 通过证据一致性校验标记不支持声明 |
| `not_verifiable` 被误计为支持 | 单独记录 `not_verifiable`，不自动算作 `supported` |
| 图片功能被误解为自动分类 | 页面明确 V1.0 图片仅用于病例资料 |
| 患者端过度诊断 | 患者端只显示通俗解释、关注/就医建议和引导 |
| 实验与系统割裂 | 分析任务、报告、实验均记录版本信息 |

- 不改动核心研究代码。
